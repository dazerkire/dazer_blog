## 写在前面

近期，笔者在进行一些自研模型的优化和线上化工作，因此开始系统学习 LLM 推理相关的内容。推理性能是一个很容易被术语淹没的话题：KV Cache、量化、连续批处理、投机解码、vLLM、TensorRT-LLM……它们分别解决什么问题，又该如何放在同一张图里理解？

这个系列准备从一次实际请求开始，逐步整理模型计算、服务系统和性能优化之间的关系。暂定会覆盖以下主题：

1. 一次 LLM 在线推理是如何完成的：应用、流程与指标；
2. 从指标到瓶颈：如何分析 Prefill、Decode 和服务链路的性能；
3. KV Cache、请求调度与并发；
4. 量化的原理、收益与约束；
5. 投机解码的基本机制、不同方案和线上取舍；
6. 推理引擎与框架：vLLM、TensorRT-LLM 等设计的侧重点。

本篇是开篇，不讨论具体优化手段，也不试图给出某个框架的使用指南。目标是先回答三个更基础的问题：LLM 如何完成一次生成？不同应用如何改变一次请求？又该用什么指标描述它快不快？后续文章会从这些指标出发，再进入具体的性能分析与优化。

## 从一句问答开始

假设我们向一个在线 LLM 服务发送请求：

```text
用户输入：Hi, what's your name?
模型回复：Hello! I'm an AI assistant.
```

从用户视角看，这像是一次简单的问答：输入一句话，模型返回一句话。但服务端并不是一次性“写出”整段回复。它首先使用模型对应的 tokenizer 将输入转换为 Token ID；不同模型的 tokenizer 不同，因此不必把英文单词、标点或字符简单地等同于一个 Token。这里仅把输入抽象为一个很短的 Token 序列：

```text
"Hi, what's your name?"
  ↓ tokenizer
[x₁, x₂, x₃, …, xₙ]
```

自回归语言模型要做的，是在已有上下文的条件下预测下一个 Token。模型首先得到的是下一个 Token 的概率分布：

$$
P(x_{t+1} \mid x_1, x_2, \ldots, x_t)
$$

这个预测由 Transformer 完成。Transformer 的 self-attention 机制最早由 Vaswani 等人在 *Attention Is All You Need* 中系统提出 [1]；主流自回归 LLM 通常采用其 decoder-only 变体。下图不是原论文结构图的复制，而是为在线生成过程重新绘制的简化视图：

![Decoder-only LLM 的一次自回归生成：Prompt 经 Tokenizer、Causal Attention、MLP、LM Head 和采样后得到下一个 Token；KV Cache 在后续 Decode 中被复用。](/assets/images/posts/llm-inference/decoder-only-inference-flow.png)

*图 1：Decoder-only LLM 的一次自回归生成流程。*{: .text-center .d-block .mt-2 .mb-4 }

图中的 **Causal Self-Attention** 表示当前位置只能关注已有的 Token，不能读取未来 Token；这正是生成必须逐步进行的原因。模型经过多层 Decoder Block 后，由 LM Head 得到词表上每个候选 Token 的分数（logits），再由采样策略选出下一个 Token。生成第二个及之后的 Token 时，历史 Token 的 Key 和 Value 会以 KV Cache 的形式被复用；它的具体内存与性能问题留到后续文章展开。

假设第一个输出 Token 对应 `Hello`，它会被追加到上下文；模型随后才能预测下一个 Token。这个过程不断重复，最终形成完整回复：

这个循环可以概括为：处理已有上下文 → 预测并选择一个 Token → 将它追加到上下文 → 继续下一轮，直到生成结束。

因此，用户看到的一段文本，本质上是一串彼此依赖的预测步骤。后一个 Token 要以前一个 Token 已经被选定为前提，在线生成通常不能像训练那样一次并行算出完整答案。

这里已经可以看到两个不同阶段。模型需要先处理已有输入，准备预测第一个输出 Token；这个阶段称为 **Prefill**。之后，它才进入逐 Token 产生回复的循环；这个阶段称为 **Decode**。对于这个很短的问句，二者的差异并不明显；但当输入变成长文档、几十轮对话历史，或 RAG 检索出的多段资料时，前者的成本会显著增长。

## 应用形态如何塑造一次推理请求

聊天、RAG、Agent 和批量处理最终都会调用语言模型，但它们并不是同一种推理请求。对服务端而言，区分它们时最重要的并非应用名称，而是以下几个量：

```text
输入长度：Prompt 有多长
输出长度：需要生成多少 Token
调用次数：一次用户任务要调用模型几次
返回方式：等待完整结果，还是边生成边返回
```

这些量决定了用户会等待什么，服务端又应当优先优化什么。

**对话与文本创作：一次较直接的生成请求。**

对话和文本创作是最经典的场景，也是上一节的例子：用户给出消息，模型基于系统提示词、历史对话和当前问题生成回复。

```text
系统提示词 + 历史消息 + 当前用户问题
  → 一次 Prefill
  → 多轮 Decode
  → 流式返回文本
```

用户输入的 `Hi, what's your name?` 很短，但真实发送给模型的 Prompt 往往还包含聊天模板、系统提示词和历史消息。因此，服务端实际处理的输入通常比用户看到的文本长得多。对于这类交互式请求，最直接的体验指标是：用户多久看到第一个字，以及后续文字能否连续出现。

**RAG：先扩展上下文，再让模型生成。**

RAG 的关键不只是“模型在回答前检索资料”，而是检索结果会被拼进 Prompt：

```text
用户问题
  → 检索相关文档
  → 文档片段 + 指令 + 问题组成 Prompt
  → LLM 生成回答
```

因此，RAG 主要改变的是输入长度。即使最终答案不长，处理长上下文的 Prefill 也可能成为主要成本；检索、重排序和上下文构造同样会进入端到端延迟。分析 RAG 的性能时，不能只看模型的生成速度。

**Agent 与工具调用：一次任务可能对应多次推理。**

Agent 的基本形态是模型在多轮循环中决定下一步操作：

```text
用户任务
  → 模型判断下一步
  → 调用工具 / 读取结果
  → 将结果加入上下文
  → 再次调用模型
  → ……
```

它的特殊之处不在于单次生成的原理不同，而在于一次用户任务可能包含多次彼此依赖的模型调用。工具结果、历史决策和中间文本会持续加入上下文。因此，Agent 同时受到单次请求延迟、调用轮数、工具延迟和上下文增长的影响。

**批量任务：优化目标与在线服务不同。**

离线摘要、数据标注和批量内容生成也会经历 Prefill 与 Decode，但通常没有用户在页面前等待。它们更关心单位时间完成多少请求或多少 Token，以及为此付出的成本。

这意味着，同一个模型和同一份输入，在聊天服务与离线批处理场景中，可能需要完全不同的调度与优化策略。

| 应用形态 | 主要变化 | 通常更敏感的部分 |
| --- | --- | --- |
| 对话 / 创作 | 输出长度、流式返回 | 首 Token 与后续输出的等待时间 |
| RAG | 输入长度、检索链路 | Prefill、端到端延迟 |
| Agent | 调用轮数、上下文累积 | 总时延、工具等待、上下文增长 |
| 批量任务 | 并发与批量规模 | 吞吐、成本 |

本文聚焦文本 LLM。图像、音频等多模态输入会改变输入编码与 Prefill 的组成，但文本生成阶段仍遵循相似的自回归 Decode 过程。

## 一次在线推理请求的完整生命周期

上一节讨论的是应用如何决定请求形态。无论应用属于哪一类，当最终 Prompt 已经确定，推理引擎都需要沿着一条相对稳定的路径处理请求：

![一次在线 LLM 请求的完整生命周期：请求经过 Prompt 构造与 Tokenizer、排队调度、Prefill、首 Token、Decode 循环和流式返回，最后释放状态；KV Cache 在 Decode 阶段被使用。](/assets/images/posts/llm-inference/online-inference-lifecycle.png)

*图 2：一次在线 LLM 请求的完整生命周期。*{: .text-center .d-block .mt-2 .mb-4 }

RAG 的检索、Agent 的工具调用等步骤可能发生在一次模型调用前后；而模型引擎本身主要负责 Tokenize、调度、Prefill、Decode 和输出。端到端延迟需要同时考虑这两层。

**构造 Prompt：模型看到的内容不等于用户输入。**

以聊天请求为例，服务端通常会把系统提示词、历史消息和当前问题套入模型对应的 chat template。RAG 则会在此之前加入检索出的文档片段。

```text
用户可见消息 ≠ 模型实际处理的 Prompt
```

因此，分析输入长度时，应以最终 Prompt 的 Token 数为准，而不是只看用户在输入框中键入了多少字。

**排队与调度：请求不一定立刻开始计算。**

在线服务通常同时接收多个请求。GPU 显存、可用 KV Cache 空间和当前批次容量有限，因此请求可能在队列中等待，或被与其他请求组成 batch 后才开始执行。

排队不会改变模型输出，却会直接增加用户等待时间。这也解释了为什么一个低负载下很快的模型，在高并发时可能迟迟不返回第一个字。

**Prefill：处理完整输入，准备第一个输出 Token。**

Prefill 会处理已经确定的完整 Prompt，得到预测第一个输出 Token 所需的状态。与此同时，模型会保存后续生成需要复用的历史注意力状态；这就是 KV Cache 的基本作用。这里暂不展开其内存布局和优化方式，只需记住：它避免了生成每个新 Token 时从头计算整段历史。

**Decode、采样与流式回传：从第一个 Token 开始生成。**

模型得到 logits 后，服务端根据采样策略选出第一个 Token，例如 `Hello`。在流式服务中，这个 Token 可以立刻回传给用户；随后它被追加到序列，模型执行下一轮 Decode，继续生成 `!`、` I'm`、` an` 等 Token。

生成直到遇到结束标记、达到最大输出长度，或被用户取消。服务端随后释放该请求占用的 KV Cache 等状态，为后续请求腾出资源。

## 如何描述一次推理的性能

同一个服务可以很快返回第一个字，却在后续生成中断断续续；也可以首字稍慢，但在高并发下完成更多工作。因此，“快”必须被拆成对应不同阶段的指标。

**TTFT：第一个 Token 何时出现。**

**TTFT（Time To First Token）** 是从请求开始到客户端收到第一个输出 Token 的时间。它大致包含：

```text
应用侧准备 + Tokenize + 排队与调度 + Prefill + 首 Token 采样与传输
```

对交互式对话和 RAG，TTFT 往往是最直接的“响应是否及时”指标。长 Prompt、长队列、检索慢或 Prefill 慢，都会拉高 TTFT。即使模型后续生成很快，只要用户迟迟看不到第一个字，体验仍然会很差。

**ITL 与 TPOT：后续 Token 是否连续出现。**

第一个 Token 返回后，用户会继续看到：

```text
Hello → ! → I'm → an → AI → assistant
```

**ITL（Inter-Token Latency）** 描述相邻两个输出 Token 到达之间的时间间隔。实践中也常用 **TPOT（Time Per Output Token）** 描述首 Token 之后，平均每生成一个输出 Token 所需的时间。

不同系统或论文对 TPOT 的统计口径可能略有不同。本文采用以下约定：ITL 关注每一步的间隔，TPOT 关注这些间隔的平均值。对于流式聊天，TPOT 越小，文字看起来越连贯；它主要反映 Decode 循环的速度，也可能受到批处理、调度和网络传输影响。

**端到端延迟：完整答案何时完成。**

端到端延迟从请求发出开始，到完整响应接收完成为止。若输出共有 `M` 个 Token，可以用下式建立直觉：

$$
T_{\text{end-to-end}} \approx \operatorname{TTFT} + (M - 1) \cdot \operatorname{TPOT} + T_{\text{tail}}
$$

这不是严格公式，因为每一步 Decode 的耗时并不完全一致；但它说明了不同工作负载的差异：长输入、短输出时，TTFT 往往更关键；短输入、长输出时，TPOT 的累积影响更大；两者都长时，则需要同时关注两条路径。

**吞吐、并发与排队：从单个请求到整个服务。**

前面的指标关注单个用户请求。服务端还要看整体效率：

- **请求吞吐**：单位时间完成多少请求；
- **Token 吞吐**：单位时间处理或生成多少 Token；
- **并发度**：同时处于处理或生成状态的请求数；
- **排队时间**：请求在真正开始执行前等待多久。

吞吐高不一定意味着单个用户更快。服务端为了提高 GPU 利用率，可能把更多请求组成 batch；这常能提升总吞吐，却也可能让单个请求等待更久、TTFT 变差。

在线指标还应关注 p50、p95、p99 等分位数：平均值容易掩盖高并发下的排队和长尾，而尾部延迟往往更接近用户真正抱怨的问题。

| 指标 | 回答的问题 | 主要对应阶段 |
| --- | --- | --- |
| TTFT | 多久看到第一个字？ | 排队、调度、Prefill |
| ITL / TPOT | 后续文字是否连续？ | Decode、采样、流式传输 |
| 端到端延迟 | 完整答案多久完成？ | 全链路 |
| Token 吞吐 | 系统每秒完成多少模型工作？ | 批处理、调度、硬件利用 |
| p95 / p99 | 高负载时体验是否稳定？ | 队列与资源竞争 |

## 小结

一次 LLM 在线推理并不是一次孤立的模型前向。它从 Prompt 构造开始，经过排队、Prefill、逐 Token Decode、采样和流式传输，最后才形成用户看到的完整回答。不同应用改变了输入、输出和调用方式，因此关注的性能指标也不同。

到这里，还没有讨论量化、PagedAttention、连续批处理或投机解码等具体手段。但已经可以明确描述：一次请求慢在什么阶段，用户感受到什么，以及不同业务为何会得到不同的性能结论。
