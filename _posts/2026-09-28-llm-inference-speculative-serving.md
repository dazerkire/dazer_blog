前两篇把投机解码的成本与设计空间在单流口径下算完了：验证近乎免费、行数不占时间、加速比 1.5–3x。但那些数字有一个共同的隐含前提：机器上只有这一个请求。真实的在线服务不是这样——batch 里挤着几十上百个请求，draft 与验证要和普通 Decode 共享每一次迭代。

第六篇末尾留的钩子正是这里：DSpark 把「验证长度」当成随引擎吞吐状态调节的量，说明投机进入服务后，成本结构发生了实质变化。本篇把投机放进第三篇的服务成本模型，算清一个问题：**单请求的加速，在什么条件下转化为服务吞吐，什么条件下不**。

## 服务端的一轮长什么样

先回顾第三篇的成本模型：普通 Decode 一次引擎迭代处理 $B$ 个请求，各出一个 Token，字节 = 15.0 GB 权重加 $B\times0.268$ GB 上下文 KV，耗时 $T(B) = (15.0+0.268B)/4.8 = 3.125+0.0558B$ ms；$L=2048$ 下永远字节主导，吞吐渐近 17.9k tok/s，KV 容量上限约 500 路并发。

投机进来后，一轮的形态变了，但变化方式比直觉的温和。两件事同时发生：

**draft 也可以批处理。**$B$ 个请求的 draft 第 1 步合成一个 batch 前向（读一遍 draft 权重，各读各的 draft 上下文 KV），第 2 步再一个，依此类推。第五篇单流里 draft 是 4 个独立小步；服务里它是 4 个正常的 decode 迭代，权重同样在批内摊销。外部 1B draft 一步的字节是 $2.5+0.067B$ GB，FLOPs 项 0.16 ms 量级，也是字节主导。

**验证行进 batch，行数只乘 FLOPs、不乘字节。**每个投机的请求在这轮的验证迭代里贡献 $k+1=5$ 行，但 5 行同属一条序列、共享同一段上下文 KV——第五篇的机制在 batch 维度原样重现：跨请求共享权重，跨行共享 KV。验证迭代的字节项与普通迭代**完全相同**，多出来的 4 行只把 FLOPs 项从 $16.1B$ 推到 $5\times16.1B$ GFLOPs。

于是一轮 = 4 个 draft 迭代加 1 个验证迭代，共 5 个引擎迭代。成本的全部变化集中在两处：draft 段新增的字节，验证段翻 5 倍的 FLOPs。

## 验证行的免费边界

把验证迭代的两个项写出来：

$$
\text{字节项} = \frac{15.0+0.268B}{4.8} = 3.125+0.0558B,\qquad
\text{FLOPs 项} = \frac{5\times16.1B}{989} = 0.0814B\ \ (\text{ms})
$$

字节项有截距（权重 15 GB）、斜率平（每请求 0.268 GB）；FLOPs 项无截距、斜率陡（5 行）。两者相交于：

$$
0.0814B = 3.125+0.0558B\ \Longrightarrow\ B^{\ast}\approx122
$$

这就是**验证行的免费边界**：$B<122$ 时验证迭代字节主导，5 行白给；$B>122$ 后 FLOPs 项反超，每多一行按 0.0163 ms 全额计价，每个投机请求的边际成本（0.0814 ms）比普通请求（0.0558 ms）贵 46%。122 个请求乘 5 行约等于 610 行，是全 batch 合计的免费额度——对照第六篇单流口径的约 196 行：那是一个请求能白拿的行数，这是整个引擎能白拿的。

图 1 里还有一条对照线：普通 Decode 自己的 FLOPs 项（$0.0163B$ ms），斜率永远低于字节项，任何 $B$ 都追不上——这正是第三篇「61k 算力天花板在 $L=2048$ 下够不着」的另一面。投机做的事是把这个斜率乘上 $k+1$：**它把闲置算力兑换成 Token 的同时，让自己成了算力的第一个大客户**。单流时算力无限白给，服务里白给的部分是有限的，这就是两个世界的分界。

## B=64：一个反直觉的起点

现在可以算完整对比了。$B=64$（全部请求投机，$\alpha=0.8$，$E[N]=3.36$）：

```text
draft 批处理：一步 2.5 + 64×0.067 = 6.79 GB → 1.41 ms；4 步共 5.66 ms
验证迭代：    max(6.70, 5.21) = 6.70 ms（B=64 < 122，字节主导）
普通迭代：    6.70 ms，产出 64 Token
```

| | 耗时 | 产出 | 吞吐 |
| --- | --- | --- | --- |
| 普通迭代 | 6.70 ms | 64 tok | 9.55 tok/ms |
| 投机一轮（4 draft + 1 验证） | 12.36 ms | $64\times3.36=215$ tok | **17.4 tok/ms** |

**理想口径下加速比 1.82x，吞吐接近翻倍**。这与「高并发要关投机」的日常印象不符，而分歧的来源值得看清楚：投机一轮的每 Token 字节成本是 $59.3/215\approx0.28$ GB，普通迭代是 $32.2/64\approx0.50$ GB——15 GB 的权重读取被摊到 3.36 倍的 Token 上。在 $B$ 还不大的区间，投机改善吞吐的机制与单流完全相同：固定字节项的摊销倍数变大了。

所以「高并发关投机」不是全局真理，而是有条件的。条件是什么？往下看四条侵蚀。

## 收益的四重侵蚀

**一，渐近极限打折。**$B\to\infty$ 时常数项消失，一轮的斜率由 draft 段字节（$0.0558B$）加验证段（$B>122$ 后取计算项 $0.0814B$）构成：

$$
\text{渐近吞吐} = \frac{3.36}{0.0558+0.0814}\times1000 \approx 24.5\text{k tok/s} = 1.37\times17.9\text{k}
$$

外部 draft 的服务端渐近收益从单流的 1.82x 降到 1.37x。直觉公式 $E[N]/(1+kr)$ 会给 1.68x，高估了——它没算验证段在 $B>122$ 后翻成计算计价。draft 段的斜率大头是它自己的上下文 KV：串行 4 步，每步读一遍 0.067 GB，加起来正好等于 target 读一遍的 0.268 GB。**draft 的上下文读取不摊销，是外部 draft 在服务端最主要的额外开销。**

**二，轻头的收益被计算接管。**换成单层头（EAGLE/MTP 类）：draft 上下文 KV 是 target 的 1/32，draft 段斜率塌到 0.007B；渐近斜率变成 $0.007+0.0814$，与整轮的计算斜率几乎重合，渐近吞吐约 38k tok/s（2.1x）。头越轻，收益越往 989 TFLOPS 的计算天花板靠——**单流世界里「行数免费」的遗产，在服务端兑换成的是算力，而算力上限成了新约束**。

**三，大树几乎立刻撞墙。**45 节点的树把验证 FLOPs 斜率抬到 $45\times0.0163 = 0.733B$ ms，与字节项的交点在 $B^{\ast}\approx4.6$：**batch 超过 5 个请求，验证就纯计算计价**，每个投机请求的边际成本是普通请求的 13 倍。按树形 $E\approx4.1$ 算，$B=64$ 时吞吐只剩约 5k tok/s，不到普通的六成。第六篇里单流最优的配置（大树换覆盖），在服务里是最先该关的；服务友好的是链形小 $k$。**单请求最优与服务最优在形状这一维上正式分家**，树的宽度必须随负载收缩。

**四，$T_{\text{other}}$ 吃掉理想值。**一轮 5 个引擎迭代，每个都付 kernel 启动、采样、同步这些杂项；普通侧 3.36 个 Token 本来只需要 3.36 个迭代。按第二篇的 2.6 ms 估：杂项统一则加速比 1.23x，draft 栈轻、杂项减半则 1.55x。**真实加速比落在 1.2–1.55x 之间**——EAGLE-3 在 SGLang、$B=64$ 报告的 1.38x 正好在这个区间里 [2]。

四条侵蚀合起来的图景：投机的吞吐收益从单流的 1.5–3x 收敛到服务端理想口径的 1.4–2.1x，再被杂项压到 1.2–1.5x；配置不当时（大树、过大的 $k$）直接转负。收益仍在，但需要按负载管理。

## 调度与 SLO

管理的方式是分负载区决策：

| 负载区 | 状态 | 投机的行为 |
| --- | --- | --- |
| 低载（B 远小于 122） | 字节主导，算力闲置 | 单流逻辑几乎原样成立，收益 1.5–2x，全开 |
| 中载（接近 122） | 验证仍字节主导，杂项折扣显现 | 收益 1.2–1.55x，链形小 $k$ 服务友好 |
| 饱和（B > 122 或大树下 B > 5） | 验证计算计价，边际反超 | 全局开会亏，需要逐请求决策 |

「每请求开关」比「全局开关」多出的自由度：负载在请求间不均匀（上下文长短、接受率高低各异），全局开关只能对平均值负责，逐请求开关能让边际收益为正的请求继续投机、为负的退出。这个方向的抓手不止一个：Online Speculative Decoding 把 draft 本身做成在线适配的，用观察到的真实查询蒸馏更新 draft，接受率提高 0.1–0.65、延迟再降 1.42–2.17x [3]；DSpark 调度的是验证——按前缀存活概率估计「后缀还值得验证吗」，按吞吐画像知道「系统现在缺什么」，把验证长度从 $k$ 连续收到 0（退化为普通 Decode）[1]。开/关的二值决策由此变成连续旋钮，削掉的是注定被拒的验证行，正是计算计价区间里最贵的那部分。

延迟指标的变化不对称。TTFT 不变：首 Token 走常规路径。TPOT 均值改善（单流口径 3.2 → 1.59 ms）。但 **p99 恶化**：一轮产出在 1 到 5 之间波动，全接受的轮 5 个 Token 连发（间隔近零），首拒的轮付全部 5.34 ms 只兑现 1 个 Token。$\alpha=0.8$ 时慢轮概率 $1-\alpha=0.2$，连续慢轮就是尾：粗算 p99 每 Token 约 5.3 ms，对比普通 Decode 的恒定 3.2。**均值从 3.2 降到 1.59，p99 从 3.2 升到 5.3**，流式用户感知为「一阵快、一阵停」。对 ITL 有 SLO 的服务，削验证长度因此有第二个理由：砍后缀同时削了尾。

容量是最后一个小项。瞬态 KV 槽每轮 $k+1$ 个：$L=2048$ 时占上下文的 0.25%，可忽略；短上下文的 Agent 负载（$L$ 为几十）时占到接近一成，加上 draft 权重本身占显存（外部 1B 是 135 GB 预算里的 2%），短上下文高并发场景需要把容量项算进去再开。

## 统一判据与选型

把前面几节的推导收成一个判据：**投机的边际 Token 成本是否低于普通 Decode 的边际成本（0.268 GB/Token 的 KV 带宽），且没有先碰到算力、显存或尾延迟的更紧约束。**边际成本由四项组成：

$$
\frac{k\cdot r\times0.268}{E[N]}\ (\text{draft 段字节})\ +\ \text{验证 FLOPs（是否计价看 }B\text{ 对 }B^{\ast}\text{）}\ +\ \text{瞬态显存}\ +\ \frac{(k+1)T_{\text{other}}}{E[N]}
$$

第一项里 $r$ 是 draft 与 target 的每 token KV 之比，头越轻越近零；第二项在 $B<B^{\ast}$ 免费、之后按行全价；第三项长上下文可忽略、短上下文要管；第四项是杂项放大。这是提纲里那句「额外工作是否换来了更少的 target step」的量化版。

| 场景 | 建议 | 依据 |
| --- | --- | --- |
| 低载、单流为主的实例 | 按第六篇单流选型，全开 | 行数免费、算力闲置 |
| 中载在线服务 | 链形 $k$=3–5 或单 MTP 头；监控 $B$ 与 $B^{\ast}$ 的距离 | 收益 1.2–1.55x，链形对 batch 友好 |
| 吞吐优先、接近饱和 | 逐请求收验证长度（DSpark 式）或关 | 验证计算计价，边际反超 |
| 大 $k$、大树配置 | 服务端禁用或随负载收缩 | $B^{\ast}$ 低至个位数 |
| ITL SLO 严的流式 | 关注 p99；削后缀、限 $k$ | 慢轮概率 $1-\alpha$，尾变重 |
| 短上下文高并发 Agent | 先算容量项 | 瞬态 KV 槽占比升高 |

## 小结

单流到服务的转换率可以这样读：单流 2.0x，$B=64$ 理想 1.82x（字节摊销机制原样成立），实测 1.38x（$T_{\text{other}}$ 吃掉差额），渐近 1.37x（外部 draft）到 2.1x（轻头，计算接管），配置不当时转负（大树在个位数并发后）。全部故事围绕一条主线：**行数什么时候计价**。$B^{\ast}=122$ 是这个口径下服务端的新常数，它由字节项的截距（权重）与每行 FLOPs 的斜率之比决定；负载爬向它时，投机的每一个参数（$k$、树的宽度、每请求开关）都应该相应收紧。

调度由此成为投机解码在服务端的主战场：验证长度、投机对象、树形状都是随系统状态调节的量。下一篇离开投机解码，回到地面：这些机制与前三篇的调度、显存、量化设计，在 vLLM、TensorRT-LLM、SGLang 这些推理引擎里分别如何落地，选型时如何比较。
